CRITICAL THINKING QUESTIONS

🧠 Q1: Why Did We Recommend `dev:minimal` for Daily Work?
___________________________________________________________________________
___________________________________________________________________________

→ Answer: 
   • 8-second startup (vs 30s with full Redis)
   • No wasted resources (you rarely test full cache layers)
   • Easier local debugging (fewer moving parts)
   • Same database as production (SQLite is fine for local testing)
   • When you NEED Redis testing, use `pnpm dev` instead

═══════════════════════════════════════════════════════════════════════════════

🧠 Q2: Why 70% Coverage Instead of 90%?
___________________________________________________________________________
___________________________________________________________________________

→ Answer:
   • 70% catches real bugs (main code paths)
   • 80-90% has diminishing returns (edge cases)
   • 100% is perfectionism (nearly impossible)
   • 70% + pre-commit hooks + manual review = 95% in practice
   • Philosophy: Pragmatic, not perfect

═══════════════════════════════════════════════════════════════════════════════

🧠 Q3: Why Defer `datos.ts` Refactoring If It's 109KB?
___________________________________________________________________________
___________________________________________________________________________

→ Answer:
   • Build time is acceptable (<60s target)
   • No performance complaints yet
   • Refactoring is risky (could break rates)
   • Benefit unclear (might save 100ms)
   • Better decision with metrics: refactor when build time > 60s
   • Philosophy: Don't optimize without data

═══════════════════════════════════════════════════════════════════════════════

🧠 Q4: Why Is Pre-commit Hook Setup Critical for Teams?
___________________________________________________________________________
___________________________________________________________________________

→ Answer:
   • Prevents accidentally committing secrets (huge risk!)
   • Enforces code style (no style wars on PRs)
   • Catches lint errors before they hit CI
   • Saves time (fail fast, fix locally)
   • Team culture (everyone follows same rules)
   • Scales to 50+ people (not 5 people)

═══════════════════════════════════════════════════════════════════════════════

🧠 Q5: Why Was the Monorepo Structure More Important Than It Seemed?
___________________________________________________________________________
___________________________________________________________________________

→ Answer:
   • Incorrect `src/*` in packages broke dependency resolution
   • Turborepo couldn't understand the graph
   • Builds could cascade unnecessarily
   • Team wouldn't know which package owns which feature
   • Just removing 1 line fixed it, but impact was huge
   • Philosophy: Get fundamentals right first, optimize later
